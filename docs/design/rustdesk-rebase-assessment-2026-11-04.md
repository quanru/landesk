# LanDesk 重新基于 RustDesk 的评估

日期：2026-11-04。评估现有 LanDesk 的维护路线，未实施迁移。结论依据固定源码、三方合并预演和文本补丁检查；本轮未编译或运行新的应用。

## 主要发现

### 高优先级：更换源码基线不能代替 LAN 安全层的迁移

当前连接入口 `src/client.rs:288` 先做私网端点解析、候选选择及签名握手；`src/server.rs:155` 在握手前限制未认证连接；`src/server/connection.rs:1840` 校验加密状态、LAN 登录、失败限流及用户名密码。`libs/hbb_common/src/config.rs:1084` 起管理本地凭据，`libs/hbb_common/src/lan.rs:117` 限制地址范围。

官方 RustDesk 已有直接 IP 分支（本次固定版本的 `src/client.rs:440`），但它不能自动替代 LanDesk 现有的协议、凭据、指纹和发现模型。当前原生及 `web/` 浏览器客户端也依赖同一 LAN 协议。迁移时若直接恢复原版认证，已有客户端、保存的凭据及网关都可能失配。第一阶段应保留当前 LAN 协议及设备身份；若之后要改协议，再独立设计版本协商和过渡，不能顺带静默改变。

`libs/base/protos/message.proto:1054` 处已有明确冲突：LanDesk 的字段 33／34 是 LAN 握手、35 是端口转发、36 是安全 OS 登录；官方当前 33／34 分别是端口转发和 OS 登录。不能替换 proto 后只重新生成桥接就宣称兼容。长期可以评估独立 LAN 消息封装，但这是额外协议工程，不是本轮已验证的方案。

### 高优先级：同步成本主要来自改动边界，重新基于官方本身不会消除分叉

现行 `docs/local-only-scope.md:7` 不仅要求没有公网连接行为，还明确记录云账号、更新器、插件及旧 UI 已从源码删除。`scripts/check_lan_only_residuals.sh` 也检查源码、依赖及桥接符号。直接在新版 RustDesk 上重复删除这些模块，仍会持续碰到上游的修改／删除冲突。

较容易维护的候选是：保留官方源码结构，LanDesk 构建通过清晰的编译与启动边界只选择 LAN 实现，产品入口只开放所需功能，并验证最终产物不会启动或回退到公网连接。这个候选需要具体实现和验证，且与当前“从源码删除”的记录不同；不能在用户未决定前自动降低现有约束。

如果必须坚持仓库中也完全没有这些实现，就应接受持续维护一组删除补丁；重新基于官方仍能取得当下修复，但长期同步收益会缩小。Tailscale 本身的连接方式仍是独立范围，不能由 LanDesk 的私网直连承诺推导其 VPN 内部从不使用中转。

### 高优先级：common 也是迁移的一部分

当前子模块固定到 `2e7979e`，官方主应用固定到另一个 `fae47e0`。当前 common 在 SubnetDesk 基础上又叠加了 6 个本地提交，涉及私网检查、配置存储、云账号移除、流参数和帧限制；与官方当前 common 对照有 22 个路径差异。官方 Stream 是支持多个传输的 enum，当前 LAN 版封装不同，不能只改 `.gitmodules` URL 或 gitlink。

有利条件是：官方当前 common 已有 `Stream::set_max_packet_length`，不必再次为这一项维护专门 setter。新的 LAN 传输可以优先适配官方 Stream，客户端专属认证与发现尽量放主应用。是否最终能取消 common fork，取决于底层私网限制与配置接口能否保持相同安全语义，当前不能保证。

### 中优先级：差异大，但可保留的产品功能并不少

本轮找到了 16 个相对采用的 SubnetDesk 基线新增的产品 Dart 模块，包括虚拟按键、快捷键编辑器、虚拟鼠标、会话侧栏、手势缩放、连接面板、主题和来源许可展示。它们向官方当前源码临时索引逐个执行 `git apply --cached --check` 均通过。虚拟快捷键发送已有 `RemoteKeyWriter` 回调边界（`flutter/lib/mobile/widgets/remote_shortcut.dart:59`），主题已有独立入口（`flutter/lib/theme/landesk_theme.dart:60`），适合保留。

这只是文本新增文件可放入目标树，不表示 Dart API、导入、宿主行为或整应用编译已经通过。抽查的 7 个集成文件整体差异均无法直接套用；应围绕上游当前接口重接，不能搬整份 `client.rs`、`connection.rs`、`model.dart` 或远程页面。

### 中优先级：已有产品问题应单独验收

当前 `flutter/lib/mobile/pages/remote_page.dart:529` 显式在非 iOS、手机竖屏、系统键盘可见、尚未收到第一帧等状态隐藏虚拟按键。这是现有入口规则，不能把“采用新版 RustDesk”当作虚拟键盘问题已经修好的证据。此前整幅远程画面的旋转问题也没有在最近安全修复中得到完整验收。

迁移前应明确虚拟键盘的目标平台、横竖屏及系统键盘共存规则，迁移后逐项验收。当前 Android 也不能按 iOS 虚拟按键体验直接计作已支持。本轮未判定这些隐藏条件是否就是用户此前问题的全部原因。

## 路线比较

| 路线 | 近期成本 | 长期成本 | 判断 |
| --- | --- | --- | --- |
| 当前 LanDesk 上继续选择性接入 | 最低，已有运行和发布基础可用 | 每次核对上游，核心差异大，需自行判断修复是否已覆盖 | 适合现有版本维护与必要修复，不适合作为不断扩张的逐提交追平计划。 |
| 当前分支一次合并官方 master | 冲突面最大，需恢复大量行为边界 | 合并一次并不能保证以后轻松 | 不建议直接进行；234 个冲突文件只是文本层面，清零后仍需安全与产品验证。 |
| 固定官方新基线，只移植明确的 LanDesk 功能 | 有明显一次性投入，认证、协议与发布身份必须认真处理 | 若自有改动集中、核心保持上游形状，有望明显降低后续接入成本 | 推荐先做有限原型，再决定全面迁移；不是已证实成本更低的完成方案。 |
| 官方基线加全新 LAN 协议／认证 | 初期最高，要处理旧客户端、凭据与浏览器兼容 | 可以重新设计边界，但引入新的安全维护责任 | 目前不建议把协议重做与基线迁移捆在一起。 |

## 保留什么，重新适配什么

| 功能／资源 | 处理建议 | 难度与原因 |
| --- | --- | --- |
| LAN 私网与 Tailscale 地址限制 | 保留语义，集中出站、入站与转发入口；拒绝公网和域名解析绕过 | 高：必须覆盖全部连接路径，不能只藏 UI。 |
| 加密握手、账号密码、指纹与记住凭据 | 首期保留协议与存储兼容，适配官方 Stream／会话认证边界 | 高：涉及 proto、密钥、限流、权限、浏览器和 common。 |
| 发现与设备列表 | 保留 mDNS／UDP 实现，按新接口接入 | 中：端点、设备身份、配置和 UI 均有连接点；不能假定跨子网自动发现。 |
| 虚拟键盘与鼠标 | 保留独立模块和测试，重接按键发送及生命周期 | 中：核心模块边界较好，仍须验收多点触控、松键、后台、系统键盘和横竖屏。 |
| 会话侧栏、手势、窗口概览 | 按功能移植，避免覆盖整个远程页面 | 中：与上游输入、视口和状态模型交叉。 |
| 现代主题与图标 | 优先使用现有 ThemeData／独立控件和资源 | 低至中：主题模块可复用；不要把 SubnetDesk 的整套页面布局当作主题一起搬。 |
| 文件、剪贴板、采集、游标及安装器 | 优先保留新版官方实现，只补 LAN 接入需要的差异 | 中至高：必须复核前几批 LAN 适配；“官方已含修复”不等于新入口已正确使用。 |
| 原生／Web、终端和文件传输 | 均在现行产品范围内，不能静默省略 | 高：特别是本地 HTTPS 网关及权限隔离依赖 LAN 协议。 |
| App 身份与签名配置 | 保留 iOS／Android 的 dev.quanru.localdesk、现有签名身份、配置目录与密钥身份 | 中：不需要另建 App，但每个平台都要验证覆盖升级与数据保留。macOS 显示名与内部配置名并不完全一致。 |
| 官网、README、视频、作品集 | 基本可继续使用；迁移验收后再更新版本与说明 | 低：不因应用基线改变而重建网站。采用过的 SubnetDesk 代码仍保留来源记录。 |

好的现成基础包括：独立的输入回调、主题模块、LAN 单元测试、最近补齐的原生／Flutter 回归、签名和构建记录。这些资产都应继续用，不必因采用新基线丢弃。

## 推荐的验证顺序与停止条件

第一步先锁定官方快照做有限原型。优先使用本次已核对的 `55786aaa5` 作为评估起点，并保留与正式 1.5.1 标签的差异清单；正式候选基线需要另行按验证结果确定，不把浮动 master 当稳定发行版。

原型只验证两个最有代表性的宿主：Mac 受控端与 iOS 控制端。这是阶段性验证范围，不是把 Windows／Linux／Android／浏览器从产品中删掉。必须证明：

1. 新旧 LanDesk 对端组合的加密连接、账号认证与指纹校验成立；身份变化、密码错误、公共地址及未认证请求被正确拒绝。若决定不兼容旧版，必须有明确升级方案，不能静默回退到另一套认证。
2. 真正看到桌面并能执行普通输入，虚拟按键可见、多键松开正确、横竖屏和系统键盘状态可用；不能只凭模拟预览通过。
3. LAN 构建不启动公网会合、云账号、插件下载和在线更新路径，转发也不能越过私网策略；编译开关、调用路径和行为验证一起检查。
4. 改动能收敛到 LAN 实现、认证边界、产品控件及少量启动入口；若仍需整段覆盖 client.rs、connection.rs、model.dart 和上游页面，说明目标架构还未证明能降低维护成本。

通过后，再接回其余功能与全部平台；围绕同一个发布候选验证配置／凭据迁移、设备身份、安装器、权限、文件／剪贴板／终端、网关及签名发行。本轮安全回归可以复用，受影响入口仍须重新执行。

工作量只给阶段预算，不给未经原型验证的确定交付日期：原型按数个工作日考虑；达到可替换现有多端版本的程度按周安排。原型若需要超过预先约定的数日窗口仍不能证明核心边界，应先复盘，不持续投入全面搬迁。Windows 验证环境、签名／发布要求及现存虚拟键盘和旋转问题都会影响后续预算。

本次建议是：为长期跟随 RustDesk 投入一次有明确成功条件的原型评估，当前版本继续作为可用基线；暂不开始大规模重做，也不继续以“每次多接几个提交”为完整维护路线。若坚持所有公网实现从仓库物理删除，则需要把这项长期分叉成本明确计入方案。

本轮只新增本评估与数据记录，未改应用源码、未创建迁移分支或工作树、未推送或发布。当前 common 的本地提交尚未推送，后续任何应用推送仍须先确认子模块提交可被远端获取。
